# E2 · Protocolo compartido y Registry

## Entregado

- Contrato v1: versión, lista cerrada de errores/cierres, BOARD_IDS derivados de un manifest de pizarras existentes, tipos de mensajes y operaciones por boardId/gestureId. Validadores estrictos de campos, tipos, tamaños y claves peligrosas; sanitizado de nombre de pila.
- El manifest solo incluye `prueba`. No se registran rutas de pizarras que todavía no existen.
- Registry canónico `idFromName('registry')`, SQLite, códigos de seis caracteres sin 0/O/1/I/L y reutilización con una identidad Room nueva.
- Migración de las reservas del Registry anterior `singleton`, sin cambiar la identidad de las salas reservadas. Las notificaciones de Room que todavía llegan a singleton se reenvían al Registry nuevo. La importación se marca en SQLite y no se repite en cada arranque.
- 5 creaciones/IP/hora y tope global configurable `MAX_ROOMS_PER_HOUR=100`. Se eligió 100/h como valor inicial conservador; no representa una estimación de capacidad ni un límite de facturación.
- 20 consultas de código/intentos de upgrade por IP/minuto, con contador SQLite autoritativo y binding local de Rate Limiting (20/60 s) como primera defensa. No se depende de la consistencia entre centros de datos del binding para la cuota global.
- Diez códigos inexistentes consecutivos bloquean diez minutos. Una consulta válida reinicia la racha. Respuestas 429 con Retry-After. El límite por minuto de creación se aplica antes de llamar a la autenticación externa; se verificó sin permitir ninguna llamada externa en esa prueba.
- API interna del Registry para admisión: un intento cada tres segundos por IP y pausa de un minuto tras cinco reingresos de un alumno retirado/rechazado. La llamada desde el hello autenticado de Room corresponde a E3; en E2 se prueba directamente su estado SQLite.
- Hash de IP con sal aleatoria de 32 bytes guardada en SQLite privado. Ni IP sin hash, nombres ni teacherToken se guardan en las tablas de cuotas. No se añaden logs de esos datos.
- Alarm del Registry: libera reservas cerradas al vencer RETENTION_HOURS=24 y limpia contadores/clientes caducados. Reabrir dentro del plazo elimina la fecha de liberación. Repetir un cierre no extiende la reserva.

## Compatibilidad y límites de esta etapa

El Room y el motor anteriores continúan usando `LegacyOp`. El tipo nuevo `Op` y el parser v1 quedan preparados para E3/E4. No se presenta el Room anterior como si ya validara hello v1, tuviera AUTH_TIMEOUT, diez pendientes, pausa automática, cambio de pizarra o borrado de sus datos.

La purga de la base SQLite de cada Room y sus nombres corresponde a E3. E2 libera la reserva del Registry; no equivale a haber implementado toda la retención de datos de la sala.

Las cuotas son ventanas fijas de minuto/hora. Una petición de upgrade cuenta como una consulta. Las admisiones pendientes se cargarán al completar hello en E3. El cliente de prueba de navegador usa una IP local simulada distinta de la fase de sockets del simulador para que ambos grupos no compartan artificialmente la cuota de veinte consultas.

Una prueba adicional de expulsión real del objeto con reloj simulado agotó su tiempo y afectó a la siguiente prueba de tiempo. Se separó de la batería de reloj controlado; no se afirma haber comprobado expulsión/hibernación real en E2. La prueba de persistencia comprueba la sal en SQLite y su estabilidad, y las pruebas de alarma sí ejecutan alarm con la API de Cloudflare. La recuperación real por hibernación queda para E3.
