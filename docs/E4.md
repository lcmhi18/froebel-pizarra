# E4 · Motor v1 y deshacer por usuario

## Resultado

RoomEngine usa operaciones v1 directamente y no depende de React ni del DOM. useRoom ya no traduce operaciones LegacyOp: mantiene el transporte y entrega snapshots/ops al motor. El formato antiguo queda únicamente para migrar datos históricos del Room.

El motor conserva el estado confirmado y las operaciones pendientes por opId. Aplica el estado remoto y superpone los pendientes; un eco confirma la operación sin generar historial. En reconexión reaplica y reenvía los mismos opId, aprovechando la deduplicación del servidor. Detecta huecos de seq, bloquea temporalmente la edición y solicita resync. Un rechazo descarta los pendientes afectados por esa sincronización y solicita un snapshot. No aplica operaciones de otro boardId.

Cada gesto tiene un gestureId. Los eventos intermedios se agrupan a unos 40 ms, fusionando únicamente patches/fields que aún no salieron del cliente. Los movimientos de orden mantienen su secuencia porque pueden depender entre sí. Al soltar se emite el cambio final, aunque el último movimiento ya se hubiera transmitido. Durante el gesto se protege visualmente el objeto que se está editando; los cambios remotos llegan al estado confirmado y los objetos ajenos siguen apareciendo. Al terminar se reconcilia con ellos.

El historial guarda como máximo sesenta gestos propios. Deshacer un update restaura solo sus propiedades y conserva valores que otro usuario haya sobrescrito después. No recrea un objeto actualizado que otro ya borró. Deshacer remove/Limpiar restaura exactamente los IDs originales, incluso si pertenecían a otro autor, y su orden. Si el ID ya existe se omite. Deshacer una creación evita borrar modificaciones posteriores de otra persona. Las operaciones inversas llevan la firma pública del usuario que deshace.

newId() genera IDs con prefijo del autor autenticado; la pizarra de prueba lo usa también para Gemelo. El orden viaja como id/after, sin reemplazar el array completo. Herramienta, color vigente, selección, imán y otras localKeys siguen fuera de las operaciones; el color de cada objeto sí se comparte.

## Contrato del adapter

BoardAdapter añade setReadOnly. getState entrega snapshots inmutables: los objetos no modificados conservan su referencia y nunca se muta un estado ya publicado. setState/applyRemote redibujan sin onChange ni historial local. El adapter de prueba aplica ese contrato y bloquea mutaciones en solo lectura; la pantalla también deshabilita las acciones que editan.

El diff compara referencias primero. Para referencias distintas usa una firma estructural ordenada, con hash FNV-1a y caché WeakMap; conserva el texto canónico para impedir falsos iguales por colisión. applyOperation usa copias al modificar objetos/fields, de modo que no invalida las referencias de snapshots anteriores.

La pausa/reconexión activa solo lectura. Al desmontar se cancelan temporizadores y se ignoran mensajes/snapshots atrasados; una conexión anterior no puede modificar el adapter de una sesión nueva.

## Pruebas y evidencia

- npm run test:engine: 24 pruebas en Node sin DOM. Incluyen diff v1, fusión, ecos, pendientes/reconexión, localKeys, solo lectura, limpieza, deshacer por usuario y límite de historial.
- Orden: las 120 permutaciones de cinco objetos, varios frames dentro de un gesto y sesenta secuencias deterministas de reordenamientos; convergencia y restauración del orden original, preservando adiciones remotas.
- Arrastre: ráfagas locales antes de 40 ms no generan envíos por evento; todos los frames y el final comparten gestureId y generan una sola entrada de historial.
- Rendimiento: 500 objetos, un objeto modificado y referencias estables; 100 calentamientos y 300 mediciones. Última ejecución: p95 0,258 ms, máximo 1,664 ms, frente al presupuesto de 2 ms. Mide el diff, no clonación del adapter, render, red ni dispositivos físicos. En ejecuciones anteriores hubo máximos aislados superiores a 2 ms por variación del proceso; el test exige p95 inferior a 2 ms.
- Vitest/Workers: 39 pruebas aprobadas en la batería completa (37 de E2/E3 y dos nuevas de integración E4). Los motores de profesor/alumno se conectan al Room con SQLite y WebSockets reales locales; restauran un objeto ajeno con el mismo ID y respetan la pausa del profesor.
- npm run test:e4: las 24 pruebas del motor, comprobación TypeScript y las dos pruebas de integración de E4.
- Edge local: solicitud/aceptación, dibujo bidireccional, arrastre completo, deslizador, deshacer sin quitar el texto del alumno, Limpiar/deshacer conservando data-item, recarga del profesor, expulsión/reingreso, tema oscuro y anchos 1440/768/390; sin errores de consola.
- npm run test:e1: rutas/estáticos, proxy HTTP/WS y recorrido compilado profesor → aceptar → dibujar bajo CSP.
- npm run build y typecheck aprobados. Persisten los dos avisos conocidos de React Router y el aviso del paquete de pool renombrado.

No se probaron carga sostenida con muchas salas, dispositivos físicos modestos ni todas las funcionalidades del HTML de referencia. El benchmark no garantiza el mismo tiempo en cualquier equipo ni con objetos arbitrariamente grandes. El diseño final, attach/UI vanilla y la pizarra SVG separada corresponden a E5; el cambio real entre dos pizarras corresponde a E6. app/ continúa ausente y no se modificó. Las consideraciones de migración histórica documentadas en E3 siguen pendientes antes de desplegar.

E4 se guarda en commit local y espera confirmación para E5. No hubo push, despliegue, cambios de cuenta, planes de pago ni servicios de voz.
