## Evidencia concreta

- app/package.json: React y React DOM 18.3.1, Konva 9.3.18, react-konva 18.2.10, Vite 5.4.11. Son dependencias de otro proyecto; no se instalaron ni actualizaron aquí.
- app/src/store.ts: useBoard crea items con useState y conserva ref/past/future dentro de cada instancia del hook. Retorna items, commit, undo, redo y disponibilidad del historial; no retorna setState remoto, suscripción externa, control readOnly ni fábrica de IDs inyectable. commit siempre genera un paso de historial local. No hay store singleton accesible desde un adaptador externo.
- app/src/App.tsx: App no recibe propiedades e invoca useBoard directamente (línea 24). Conserva herramientas, selección, edición, zoom, pan y controles localmente. Los botones y atajos llaman undo/redo del hook. Varias creaciones usan crypto.randomUUID directamente. Montar App tal cual no permite sustituir ese contrato desde un wrapper.
- app/src/Board.tsx: el lienzo exportado sí recibe items/commit y controles mediante props (líneas 11–15 y 82). Es un componente reutilizable desde una nueva interfaz, pero no contiene la barra completa de App. Su fábrica uid es local, no inyectable. Los arrastres mantienen preview local y commit al finalizar (líneas 113–115): un adaptador que solo observe commit no transmite el arrastre continuamente. No recibe readOnly.
- app/src/main.tsx: crea el root tras validar su propia sesión mediante /api/auth. Importarlo como entrada de otro root tiene efectos de montaje/autenticación y no es un contrato de integración de sala. El contrato Supabase/Worker de este proyecto es independiente.

No se basa esta conclusión en React DevTools, propiedades privadas de React/Konva ni lectura oculta de estado. Interceptar globalmente hooks/crypto, simular eventos del usuario o reescribir módulos durante el build no ofrece el contrato estable requerido.

## Cómo se mapearía el estado, una vez exista el contrato

Item[] puede normalizarse a items por id y order con los ids del arreglo; fields contendría únicamente parámetros compartidos explícitos. Herramienta, color elegido para futuras figuras, selección, edición, zoom y pan permanecerían locales. setState/applyRemote deben actualizar la vista sin historial ni onChange; los commits y movimientos deben emitir al RoomEngine, usando su newId y undo. Los UUID originales necesitarían una política consistente de importación a IDs de autor, sin renombrar objetos que ya participan en operaciones remotas. Imágenes en data URL necesitarían límites y estrategia acordes con los 64 KiB por mensaje y el estado máximo del servidor. Ninguno de estos requisitos se declara implementado por este spike.
